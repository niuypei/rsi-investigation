# 八项目 Walkthrough 要求核查表

本表用于核查文档是否回答用户提出的问题，不是项目能力评分。章节号对应本轮正文。“未定位”表示已检查材料不足以确认实现；“论文”不等于源码事实。

## 1. 每份文档必须回答的十项问题

| 项 | 必须交代的内容 |
|---|---|
| A 当前组合 | 谁加载模型、Harness、工具和状态；类、对象、进程、Actor 或外部服务边界是什么。 |
| B 任务执行 | 一个实际输入如何进入提示，模型怎样选择工具，结果如何反馈，任务怎样结束并保存轨迹。 |
| C 评价 | 谁根据什么规则给分，输入和分母是什么，分数由谁消费。 |
| D 成败分析 | 谁读取哪些材料，使用规则还是模型判断，如何形成修改依据。 |
| E Harness 修改 | 建议如何转换为新增、替换、删除或配置操作；具体修改哪些字段、函数、文件；行为如何改变。 |
| F 候选处理 | 谁检查、复评、接纳、拒绝、回退；候选何时进入实际执行。 |
| G 更新选择 | 谁决定改 Harness、训练模型或停止；两种更新由什么事件触发，是否互相等待。 |
| H Harness → 模型 | 哪个 Harness 产生训练记录，记录如何筛选、构造标签/奖励/掩码，算法更新哪些参数。 |
| I 模型 → Harness | 新参数怎样加载；新模型产生的结果如何重新进入 Harness 评价和修改。 |
| J 跨轮继承 | 哪些程序、技能、数据和参数保留；失败如何处理；循环什么时候结束。 |

## 3. 调用关系与证据检查标准

- 一段执行返回后，下一段明确由谁继续；异步回调、进程等待与外部命令不得省略。
- 修改必须落到具体文件、字段或对象；生成建议、写入、生效和收益验收分别说明。
- 双向协同必须标出训练触发、数据所属 Harness、新权重可见时机和后续轨迹反馈。
- 论文与代码分别标为机制一致、明确差异或实现未定位；没有源码不能判定实现一致。
- 历史输入、测试定义、既有局部检查、静态条件推演与真实运行日志分别标注。
- 缺少类或行为实现时不补造类名；有实体时提供代码链接与行号。

## 4. 本轮核查范围

SIA 正文保持此前确认版本，其余七篇全篇重写。五个有源码项目定位了主要调用、返回、触发与具体修改；两项未确认官方源码的工作仅给论文流程和工程缺口。Co-Harness、HASE 本轮重新访问论文并进行针对性代码检索，结论限定为“仍未找到可确认归属的官方仓库”。

本轮没有运行模型、Agent 服务、游戏或训练，也没有重跑前轮纯函数/参数解析检查。所有示例补丁均未写入项目源码。图已检查角色边界和控制分支结构，未渲染。源码 commit/工作树和实验摘录字节核对、引用与行号检查见[本轮记录](evidence/other_projects_call_chain_validation.json)，全体文档检查见[总校验](evidence/document_validation.json)。
